# Netlify Blobsの同時更新後の読み取り整合性を検証する

登録先: `hogehonya/month-planner`

状態: GitHub Issue登録待ち。ユーザー判断により今回のリリース作業から切り離し、後回しにする。

## 観測結果

実Netlifyサイトの独立した一時ストアに、ローカルSDKからAPIの署名付きURL経路でアクセスした。同じ日付の別フィールドを並行して保存すると、両方の応答が成功でも直後のGETに片方の値が現れないケースを1回観測した。再実行では両方の値と履歴が保持された。

延期決定時に既に開始していた12回の同時更新も成功した。一時データは清掃済みで、新しい検証は開始していない。GitHubの `hogehonya` は未ログインのため、外部Issueの作成は未実施。

これは更新消失と確定していない。読み取りが古かった可能性がある。SDKのAPI経路と、Netlify Functionsで使用するstrong consistencyの実行時経路は異なるため、本番Functionsの同時更新不具合と同一視しない。

実SDKでは新規重複、無効なETagを使う条件付き書き込みの拒否を確認した。アプリの模擬ストアテストでは別フィールドの同時更新、最大6回の再試行、履歴転記の回復が成功している。ETagが取得できない既存Blobは503として無条件上書きを防ぐ実装を維持する。

## 再現・確認手順

1. 専用の一時ストアを作り、同じ日付のslot2とnoteを並行保存する。
2. 両方の保存結果と直後のGETを比較する。
3. 値が欠ける場合、1秒・5秒・15秒・45秒後のGET、HEADとGETのETagを比較する。
4. 同じ検証をNetlify Functions実行時のstrong consistency経路で行い、API署名付きURL経路との差を確認する。
5. 試験で作成したストアのデータだけを片付ける。本番の予定は使用しない。

## 完了条件

- 古い読み取りと永続的な更新消失を証拠で切り分ける。
- Functions経由の別フィールド同時更新で両方の値と履歴が保持されることを確認する。
- 不具合が確定した場合、再現テストと最小修正を追加する。

秘密値・PIN・署名付きURLはIssueやログへ記載しない。
