# LAN版の実行環境

同じ `public` とNetlify Functionsの `createHandler` を使い、保存アダプターだけをローカルディスクへ差し替えます。Netlifyの既定export・Blobs設定は変更しません。LAN版は独立した空のストアから開始します。利用者が差分を確認して承認した場合だけ、販売準備表をオンラインからローカルへ取り込めます。自動同期・起動時コピーは行いません。固定の品目一覧と時間割既定値はソースの仕様です。トップ画面の56枠・予定1,117などは2026-10-06時点の静的な記述であり、LANストアへ取り込まれたデータではありません。

## 起動設定

Node.js 22.12以上で `npm ci` 後に `npm start` を実行します。設定はプロセス環境だけから読み込み、秘密ファイルへフォールバックしません。

| 変数 | 用途 |
| --- | --- |
| `DATA_DIR` | 必須。永続データの保存先。publicとは別の専用ディレクトリ |
| `APP_ORIGIN` | 必須。利用者の正規origin。例 `https://month-planner.honya.dev`。末尾スラッシュなし |
| `HOST` | listen先。通常は127.0.0.1、コンテナは0.0.0.0 |
| `PORT` | listenポート。既定3000 |
| `ONLINE_SOURCE_ORIGIN` | 任意。同期元のHTTPS origin。未設定時は `https://month-planner-13f9a0.netlify.app` を使用。ブラウザから変更不可 |
| `APP_REVISION` | `/healthz` で返すデプロイ済みcommit識別子 |
| `EDIT_PIN` | Infisicalの承認済みラッパーから注入。未設定ではプランナー編集を拒否 |

リバースプロキシはAPP_ORIGINのHostを保持します。転送ヘッダーによるoriginの上書きは受け付けません。API POSTは同一Originヘッダーを必須とし、運用スクリプトも明示します。販売準備表の編集は既存仕様どおりPIN不要です。LAN外へ公開しないネットワーク境界はデプロイ設定側で管理します。

## 永続化とコンテナ

Dockerfileは非rootのnodeユーザーで起動し、`/app/data` を永続ボリュームにします。bind mountする場合はUID/GID 1000が書ける専用ディレクトリを用意します。コンテナの再作成時に同じボリュームを接続します。ソースやpublicのディレクトリを保存先にしません。APP_ORIGINとAPP_REVISION、必要なEDIT_PINはデプロイ環境から渡します。healthcheckは`node local-runtime/healthcheck.mjs [期待するrevision]`でローカルHTTPの`/healthz`を確認します。NodeのHTTPクライアントでAPP_ORIGINのHostを明示し、HTTP 200・ok・revisionの一致を検証します。revision引数を省略した場合はAPP_REVISIONを使い、4秒以内に完了しない場合は失敗します。Docker・Compose・CIで同じスクリプトを使います。

初期の保存領域は `shared-planner` と `packaging-master` に分離します。キーはSHA-256のファイル名へ変換し、内容・メタデータ・ETagを一つのレコードに格納します。写真はバイト列をbase64で格納します。新規フォルダは0700、レコードは0600です。書き込みは同一ディレクトリ内の一時ファイルへの書込・fsync・atomic rename・ディレクトリfsyncを行います。途中終了で残った `.tmp` は読み取り・一覧から除外します。

CASは同一Nodeプロセス内のストア単位直列化で保護します。**一つの保存領域に対して1プロセス・1レプリカだけ**を実行します。cluster、複数コンテナ共有、複数ホストからの同時書込は未対応です。バックアップはプロセス停止中に保存領域全体を取得し、復元時も停止して同じ所有者・権限を維持します。自動バックアップ・同期は実装しません。

## 検証

`npm test` は再作成したアダプターからの永続データ読込、CAS競合、名前空間分離、写真・SKU・日付シート、既存プランナー処理、パス制限、Origin・メソッド・本文サイズ制限を確認します。`npm run check` は実行ファイルの構文を検査します。コンテナの再作成・マウント維持・実ポートのhealth確認はデプロイ側で実施します。


## 販売準備表の手動同期

LAN専用の`POST /api/online-sync`でpreview後にapplyを行います。オンラインの包装APIから読み取った商品・写真・日付別販売準備表・商品コメントを検証し、差分件数と識別可能な項目のbefore/afterを返します。ブラウザには写真のバイナリを返しません。同期元はサーバーの固定設定だけを使い、オンラインへ書き込みません。カレンダーの`shared-planner`は対象外です。

プレビューした内容を新しい`packaging-generation-<UUID>`へ準備し、利用者の確定後に`packaging-current.json`をatomic renameで切り替えます。以前の世代と初期の`packaging-master`は削除しません。プレビューのキャンセル・期限切れで作られた未採用世代も保持します。自動削除や世代復元UIはありません。バックアップは現行ポインターと全世代を含むDATA_DIR全体を停止中に取得してください。

プレビューの有効期限は10分、tokenは一回限りです。適用時にオンラインとローカルの変更を確認し、変更済みの場合は再確認を要求します。応答喪失で結果が不明な場合は、再プレビューで現在の差分を確認します。manifestは16MiB、総取得量は128MiB、レコード数は10,000、写真1件は3MiB、取得要求は15秒、preview全体は60秒が上限です。上限を超えた場合は適用せずエラーを返します。
